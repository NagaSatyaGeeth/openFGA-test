Honest assessment: does OpenFGA fit VLS's authority model?

Mapped cleanly

  • RBAC via role objects (founder/admin/director/hr_manager/manager/finance/employee), each a first-class object with its own tuples.
  • Founder-outranks-admin: pure data (which role assignee-sets get superuser_access on the founder role object), zero special-cased model logic.
  • Manageable sets (hr_manager→{employee,finance,manager}, manager→{employee}, director→{employee,finance}) as plain role→role tuples — adding/removing a manageable role is a tuple write, not a model change.
  • Reporting subtree (transitive, unbounded-depth reports-to) via one recursive relation definition — verified 2+ hops deep against the real server.
  • Org-wide vs subtree-scoped authority as an intersection (subtree_role_managed AND reports_to) — reads exactly like the English rule.
  • hr_manager/director unable to touch directors/superusers falls out for free: those roles simply never appear in their manageable-set tuples — no explicit "cannot" rule needed.

Awkward / needed workarounds

  • Comparing actor's role against target's role requires two separate tuple directions per employee (role forward-link and assignee reverse-link) — double the writes for every role assignment, purely to support traversal in both directions.
  • Per-action relations (deactivate/change_role/manage) are identical aliases of one can_act_on relation because the spec doesn't differentiate rules per action — fine here, but if VLS ever needs different rules per action, this flattens back into real modeling work.
  • "Which rule decided it" isn't a native Check output — this demo issues 3 extra Check calls against sub-relations to reconstruct a human reason. OpenFGA's own answer is just true/false (Expand gives a rule tree, but it's not a friendly one-line explanation).
  • hr_manager/director's org-wide vs manager's subtree-only scope had to be split into two separate relations (managed_org_wide_by / managed_subtree_by) rather than one relation with a scope parameter — OpenFGA has no per-tuple "mode" flag without reaching for Conditions (ABAC).

OpenFGA cannot express (needs app logic)

  • Last-active-superuser / org-lockout guard. OpenFGA relations have no cardinality/counting primitive — no "is this the last member of set X". Demonstrated live above: OpenFGA's raw Check answer stays ALLOW while an app-side guard (counting active superuser tuples outside the ReBAC graph) forces the final DENY.
  • Any rule requiring "how many X exist" or "for all Y" (e.g. "at least one active admin must always exist", "no more than N managers per team") — same limitation, same shape of workaround needed.
  • Time-bounded or workflow-state rules (e.g. "can only reactivate within 30 days") would need OpenFGA Conditions (ABAC-lite, CEL) or app-side checks — not exercised in this spike, but worth flagging since VLS's real rules may include some.
